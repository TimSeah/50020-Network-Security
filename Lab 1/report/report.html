1. Generate Network Traffic

Q: What does a successful Ping confirm? Does it mean all services on node2 are accessible?

It confirms that node1 and node2 have IP-layer reachability: packets are routed in both directions, node2 is up, and ICMP Echo is not blocked. It does not prove that services are accessible. Ping tests only ICMP; TCP/UDP services may not be running, may listen only on localhost, or may be blocked by a firewall. The reverse is also possible: ICMP can be blocked while services remain reachable.

Q: What is the main security weakness of Telnet?

Telnet sends everything, including the username and password, in plaintext. It provides no encryption, integrity protection, or server authentication, so anyone on the path can capture credentials and commands, alter the session, or impersonate the server. SSH encrypts the session, authenticates the server with host keys, and protects integrity, which is why Telnet is unsuitable for modern remote administration.

2. Packet Sniffing and Traffic Analysis

2.1 tcpdump

On node2, ip addr shows that eth0 (10.11.2.6/24) is the interface on the lab network. lo is loopback, and sink0 is a dummy interface used for off-subnet routes.

Q: What information can be identified from tcpdump output?

  • Timestamp, source and destination IP addresses and ports, and protocol.
  • IP header fields (-v): TOS, TTL, IP ID, flags (e.g. DF), protocol, and total length.
  • TCP flags (SYN, ACK, PSH, FIN), sequence and acknowledgement numbers, window, options, and payload length.
  • ICMP type (echo request/reply), identifier, and sequence number.
  • Payload contents with -A (ASCII) or -X (hex and ASCII).

Filter commands:

tcpdump -i eth0 -nn -v icmp               # Ping only
tcpdump -i eth0 -nn -v -A 'tcp port 23'   # Telnet only (ASCII payload)
tcpdump -i eth0 -nn -v 'tcp port 22'      # SSH only

Q: Can the Telnet and SSH passwords be seen in the traffic?

Telnet: yes. Each keystroke is sent in cleartext, typically one character per packet, so -A reveals the password character by character (see Figure 8). SSH: no. After the version exchange and Diffie-Hellman key exchange (Figure 7), all traffic, including authentication, is encrypted. Only lengths and timing are visible.

Q: Why is Telnet a greater risk than SSH?

A passive sniffer on the same network can recover Telnet credentials and every command and response, as Figure 8 shows, and then reuse the credentials or hijack the session. SSH exposes only an encrypted stream. Its host-key verification also prevents an attacker from silently impersonating the server.

3. Source-IP Spoofing

spoof_icmp.py (run on node1) builds one ICMP Echo Request with a forged source address from the documentation range 198.51.100.0/24 (RFC 5737):

from scapy.all import ICMP, IP, send

packet = (IP(src="198.51.100.10", dst="10.11.2.6")
          / ICMP(type="echo-request", id=0x5002, seq=1)
          / b"Network Security Lab 1")
send(packet, iface="eth0", verbose=False)

Q: What source IP does node2 observe? Is it node1's real address?

node2 sees 198.51.100.10, not node1's real address 10.11.2.5. The source IP field is chosen by the sender and is not authenticated, so a single packet's source address cannot be trusted as proof of origin.

Q: Does node1 receive the reply? Where would it be sent?

No. node2 addresses its Echo Reply to the packet's source, 198.51.100.10. That address is outside 10.11.2.0/24, so node2 routes the reply through its default route, which in this lab is the sink0 dummy interface, and the reply is discarded. No reply appears on eth0. On a real network, the reply would go toward the forged address, not the real sender. Spoofing is therefore blind: the attacker cannot see responses. This is also how reflection attacks direct replies at a victim.

4.4 Reconstruction

  1. Discovery: 10.0.2.8 resolved node2's MAC through ARP.
  2. Phase 1, about 12:36:00 (<30 s): Forged ALERT/WARN messages claimed workstation01 activity as user=root: SUDO_ROOT SUCCESS (57), FIREWALL_POLICY DISABLED (48), SSH_CONFIG MODIFIED (46), AUTHORIZED_KEY ADDED (40), and AUDIT_CONFIG MODIFIED (31).
  3. Phase 2, about 12:40:00–12:41:00: A flood of reassuring messages: SYSTEM_HEALTH OK (112), SECURITY_SCAN CLEAN (98), FIREWALL_POLICY ENABLED (75), INTEGRITY_CHECK PASS (71), BACKUP COMPLETED, and SSH_SERVICE RUNNING.

4.5 Likely objective

The attacker's goal was to poison the SOC's monitoring record. Phase 1 attributes root access, SSH-key persistence, and disabled firewall and audit controls to the trusted workstation. Phase 2 then buries those alerts under false assurance that health, scans, integrity, and firewall are normal. This produces the "operating normally" picture management wants to see. Combined with overlapping sequence numbers, the result is an inconsistent, untrustworthy log that hides the real state and misattributes activity to workstation01.

Limitation: A network capture proves the messages were forged. It cannot show whether the reported changes actually occurred. workstation01's authorized_keys, SSH configuration, firewall, and audit settings should be checked directly, and 10.0.2.8 should be isolated and investigated.

Mitigation: Authenticate telemetry (TLS with client certificates or signed messages), alert on IP-to-MAC changes and duplicate sequence numbers, and enable ARP inspection or port security on the network.
