1. Generate Network Traffic

Q: What does a successful Ping confirm? Does it mean all services on node2 are accessible?

It confirms IP-layer reachability: node2 is up, packets are delivered in both directions, and ICMP is not blocked (5/5 replies, 0% loss). It does not mean all services are accessible. Ping tests only ICMP; TCP/UDP services may be stopped, bound to localhost, or blocked by a firewall.

Q: What is the main security weakness of Telnet?

Telnet sends all data, including the username and password, in plaintext. It has no encryption, integrity protection, or server authentication, so anyone who can observe the traffic can steal credentials, read commands, or tamper with or hijack the session. SSH provides all three protections, which makes Telnet unsuitable for modern remote administration.

2. Packet Sniffing and Traffic Analysis

2.1 tcpdump

On node2, eth0 (10.11.2.6/24) is the interface on the lab network. lo is loopback, and sink0 is a dummy interface for off-subnet routes. tcpdump was run on eth0 with a filter for each protocol while node1 generated the traffic.

How the captured packets differ by protocol:

  • Ping (Figure 4): ICMP echo request/reply pairs with matching ID and sequence number; no ports. Requests carry DF; replies do not.
  • Telnet (Figure 5): TCP port 23; after the handshake, 1-byte segments per keystroke, each echoed by the server, with readable payloads.
  • SSH (Figure 6): TCP port 22; a readable version banner, larger key-exchange packets, then only encrypted payloads.

The "cksum incorrect" messages are caused by checksum offloading: tcpdump sees outgoing packets before the checksum is filled in. They are not transmission errors.

Q: What information can be identified from tcpdump output?

  • Timestamp, source and destination IP addresses and ports, and protocol.
  • IP header fields (-v): TOS, TTL, IP ID, flags (e.g. DF), protocol, and total length.
  • TCP flags (SYN, ACK, PSH, FIN), sequence and acknowledgement numbers, window, options, and payload length.
  • ICMP type (echo request/reply), identifier, and sequence number.
  • Payload contents with -A (ASCII) or -X (hex and ASCII).

Filter commands (Figures 4–6):

tcpdump -i eth0 -nn -v icmp               # Ping only
tcpdump -i eth0 -nn -v -A 'tcp port 23'   # Telnet only (ASCII payload)
tcpdump -i eth0 -nn -v 'tcp port 22'      # SSH only

Q: Can the Telnet and SSH passwords be seen in the traffic?

Telnet: yes. Each keystroke is sent as a separate cleartext segment, so -A prints the password one character per packet (Figure 5). Figure 10 shows the same credentials recovered in Wireshark. SSH: no. After the key exchange (Figures 6 and 9), everything, including the password, is encrypted. Only packet sizes and timing are visible.

Q: Why is Telnet a greater risk than SSH?

Any passive sniffer on the path can read Telnet credentials, commands, and output (Figure 10), then reuse the credentials or hijack the session. SSH exposes only encrypted data, and host-key verification detects server impersonation.

3. Source-IP Spoofing

spoof_icmp.py (run on node1) builds one ICMP Echo Request with a forged source address from the documentation range 198.51.100.0/24 (RFC 5737):

from scapy.all import ICMP, IP, send

packet = (IP(src="198.51.100.10", dst="10.11.2.6")
          / ICMP(type="echo-request", id=0x5002, seq=1)
          / b"Network Security Lab 1")
send(packet, iface="eth0", verbose=False)

Q: What source IP does node2 observe? Is it node1's real address?

node2 sees 198.51.100.10, not node1's real address 10.11.2.5. The sender sets the source IP field freely and nothing authenticates it, so the source IP of an individual packet is not proof of origin.

Q: Does node1 receive the reply? Where would it be sent?

No. node2 sends the Echo Reply to the packet's source address, 198.51.100.10, because that is the only return address it has. That address is outside 10.11.2.0/24, so node2 routes the reply via its default route. In this lab, that route is the sink0 dummy interface, where the reply is discarded, so no reply appears on eth0 (Figure 11). On a real network, the reply would go to whoever owns the forged address, so the spoofer never sees it.

The ARP request just before the spoofed packet (frame 1 in Figure 11) also came from 10.11.2.5, not the claimed source. Useful indicators besides the source IP:

  • An IP-to-MAC mismatch.
  • An off-subnet source arriving directly on the local segment.
  • A TTL that is inconsistent with the claimed origin.
  • Requests with no replies.
  • Non-standard payloads or header defaults.

4. AI-Based Traffic Analysis

Conclusion: An attack occurred. An unknown host, 10.0.2.8 (MAC 08:00:27:25:f3:ec), spoofed node1, the trusted workstation 10.0.2.6 (workstation01). It injected 800 forged messages into node2's (10.0.2.7) monitoring service: first a burst of compromise events, then a flood of false "all clear" reports.

4.4 What the attacker did

  1. Discovery: 10.0.2.8 resolved node2's MAC through ARP.
  2. Phase 1, about 12:36:00 (<30 s): Forged ALERT/WARN messages claimed workstation01 activity as user=root: SUDO_ROOT SUCCESS (57), FIREWALL_POLICY DISABLED (48), SSH_CONFIG MODIFIED (46), AUTHORIZED_KEY ADDED (40), and AUDIT_CONFIG MODIFIED (31).
  3. Phase 2, about 12:40:00–12:41:00: A flood of reassuring messages: SYSTEM_HEALTH OK (112), SECURITY_SCAN CLEAN (98), FIREWALL_POLICY ENABLED (75), INTEGRITY_CHECK PASS (71), BACKUP COMPLETED, and SSH_SERVICE RUNNING.

4.5 Likely objective

The likely objective was to deceive the SOC by poisoning node2's monitoring data while impersonating a trusted host. Phase 1 records root access, SSH-key persistence, and disabled firewall and audit controls under workstation01's identity. Phase 2 then floods the server with "all clear" reports. As a result, the latest recorded state shows the system and its security services operating normally, which is exactly the confirmation management wants. The reused sequence numbers leave node2 with contradictory logs, which explains the inconsistency the SOC noticed.

Limitation: A network capture proves the messages were forged. It cannot show whether the reported changes actually occurred. workstation01's authorized_keys, SSH configuration, firewall, and audit settings should be checked directly, and 10.0.2.8 should be isolated and investigated.

Mitigation: Authenticate telemetry (TLS with client certificates or signed messages), alert on IP-to-MAC changes and duplicate sequence numbers, and enable ARP inspection or port security on the network.
